# 4. How asynchronous tasks fit into this picture

There is one important distinction worth making because we discussed both asyncio and Celery.

| Concept                 | What it means                                                   | Where it runs                              |
| ----------------------- | --------------------------------------------------------------- | ------------------------------------------ |
| `asyncio.create_task()` | Schedules a coroutine for concurrent execution by an event loop | Within the current Python process          |
| Python thread           | An execution path sharing its process's memory                  | Within a process                           |
| OS process              | An isolated execution environment managed by the OS             | Within the operating system                |
| Celery task             | A unit of work submitted to Celery for worker execution         | In a Celery worker's execution environment |
| Redis broker            | A service that carries task messages                            | In the Redis server process                |


An asyncio task is not automatically a separate OS process or thread. It normally runs on an event loop within the current process.

Celery, by contrast, provides a task-queue framework that allows tasks to be executed by separate workers. The worker's 
execution model depends on its configured pool.

Neither mechanism changes the underlying hardware model: the CPU still executes instructions, and the OS still manages 
execution and memory.

# Final mental model

The whole system can be understood as a stack of responsibilities:

    PHYSICAL HARDWARE
    Voltage levels → Transistors → Logic gates → Digital circuits
    
    COMPUTER HARDWARE
    CPU executes instructions ↔ RAM holds active code and data
    SSD stores executable files and optional persisted data
    
    OPERATING SYSTEM
    Manages processes, threads, virtual memory, scheduling and networking
    
    PYTHON RUNTIME
    Executes Python application code and libraries
    
    WEB APPLICATION
    Uvicorn serves HTTP → FastAPI handles requests
    
    BACKGROUND PROCESSING
    Celery client submits tasks → Redis broker → Celery worker executes tasks
    
    RESULT DELIVERY
    Worker stores result → Redis result backend → FastAPI retrieves result
    → Client receives the result

The most important insight is that each layer solves a different problem. Hardware executes instructions, 
the OS manages execution, Python runs application code, FastAPI handles HTTP requests, Celery coordinates 
background jobs, and Redis provides shared messaging and data storage.

Together, these layers allow a single application to respond quickly to users while separate workers perform 
longer-running work.
